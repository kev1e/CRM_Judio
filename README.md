# Корпоративная CRM

Внутренняя CRM одной компании: задачи и стандартизированные заявки, персональные доски, Telegram-бот. Спецификация — v2.5 (папка `docs/`): утверждены Q01–Q30, REC-01, REC-02 и D032.

**Состояние:** завершён технический фундамент (S0) и срезы S1.1–S1.4: модель пользователя, политика паролей, роли и права с областями действия, журнал аудита, создание первого администратора, привязка Telegram через бота, вход в систему (логин и пароль с подтверждением в Telegram), сессии, ограничение частоты попыток, экран «Сотрудники» (создание, отключение и включение учётных записей), установка пароля самим сотрудником, отделы с руководителями (S2). задачи с доской «Мои задачи» (S3, ядро). План — в `docs/ROADMAP.md`.

## Быстрый запуск в Docker

Нужны только Docker и Docker Compose.

```bash
sh scripts/init-env.sh
```

```bash
docker compose up --build --wait
```

Первая команда создаёт `.env` со случайными локальными секретами (файл не попадает в Git). Вторая собирает образы, применяет миграции и ждёт, пока все сервисы станут healthy.

- Страница: http://127.0.0.1:3000 (открывается экран входа)
- Открывайте CRM именно по адресу `127.0.0.1`, а не `localhost`: Telegram не считает `localhost` ссылкой, поэтому бот присылает ссылки на `127.0.0.1`.
- API: http://127.0.0.1:8000/api/v1/ready

Проверка работающего стека (API, страница, задача через воркер):

```bash
sh scripts/smoke.sh
```

Остановка с удалением данных:

```bash
docker compose down --volumes
```

Без `scripts/init-env.sh` можно скопировать `.env.example` в `.env` и заменить все значения `change-me-...` вручную. С незаменённым секретом API намеренно не запускается.

```bash
sh scripts/init-env.sh
```


Затем в отдельных терминалах (бот — четвёртый, если задан `TELEGRAM_BOT_TOKEN`):

```bash
pnpm --filter @crm/api run dev
```

```bash
pnpm --filter @crm/worker run dev
```

```bash
pnpm --filter @crm/web run dev
```

```bash
pnpm --filter @crm/telegram-bot run dev
```

## Первый администратор

Первую учётную запись создаёт команда в терминале. Она работает только пока в системе нет ни одного активного администратора, пароль спрашивает в терминале и не принимает его аргументом, действие попадает в журнал аудита.

В Docker:

```bash
docker compose run --rm api python manage.py create_first_administrator --login admin --display-name "Администратор"
```

На своей машине:

```bash
uv run --locked --all-packages --directory apps/api python manage.py create_first_administrator --login admin --display-name "Администратор"
```

Пароль: не короче 12 символов и не из списка распространённых.

Команда один раз показывает одноразовый код привязки Telegram (действует 30 минут). Его нужно отправить боту CRM в личном чате: `/start КОД`. Если код истёк, новый выдаёт команда `issue_first_administrator_token --login admin` — она работает, пока ни один администратор не привязал Telegram.

## Telegram-бот и вход в систему

Вход: логин CRM и пароль, затем подтверждение в Telegram. Без бота войти нельзя — это требование безопасности, а не ошибка настройки.

1. Создайте бота у [@BotFather](https://t.me/BotFather) и запишите его токен в `.env`: `TELEGRAM_BOT_TOKEN=...`. Токен — секрет, в Git он не попадает.
2. Запустите стек вместе с ботом:

```bash
docker compose --profile telegram up --build --wait
```

3. Создайте первого администратора (раздел выше) и отправьте боту в личном чате `/start КОД`. Бот ответит, что Telegram привязан, и удалит сообщение с кодом.
4. Откройте http://127.0.0.1:3000, введите логин и пароль. Бот пришлёт запрос с кнопками «Подтвердить вход» и «Отклонить»; запрос действует 3 минуты и срабатывает один раз.

Что важно знать:

- Сессия живёт не дольше 12 часов и не продлевается. Выход, деактивация учётной записи, смена пароля и изменение прав действуют на открытые сессии сразу.
- После нескольких неудачных попыток следующая попытка откладывается на растущее время (до 15 минут). Навсегда учётная запись не блокируется.
- Если Telegram недоступен, новый вход невозможен; уже открытые сессии продолжают работать.
- Бот работает в режиме long polling и не требует публичного адреса. Он получает только адресованные ему команды и нажатия кнопок, переписку не читает и не хранит.
- Адреса, с которых открывают CRM, перечисляются в `WEB_ORIGINS`; запросы на изменение данных с других сайтов отклоняются.

## Задачи и доска

После входа открывается доска «Мои задачи»: колонки — статусы, карточки — задачи, назначенные вам. Карточку можно перетащить в другую колонку; перенос в «Готово» завершает задачу и сразу отправляет её в архив. Клик по карточке открывает окно задачи: оно только для чтения, изменения — через кнопку «Редактировать».

- **Кто что видит.** Сотрудник — только задачи, где он исполнитель. Руководитель — ещё и задачи своих отделов («Все задачи»). Суперпользователь видит все задачи, но менять их не может без отдельного права. Автор задачи, назначенной другому, её не видит.
- **Кто что может.** Исполнитель меняет название, описание, статус, срок и отмечает чек-пойнты. Приоритет, исполнителя, архив, корзину и удаление пунктов меняет руководитель отдела.
- **Чек-пойнты** не меняют статус задачи, даже если отмечены все.
- **Архив и корзина** — разные разделы. Из архива и корзины задачу возвращает руководитель.
- **Новая задача**: задачи ставит руководитель — для отдела, которым он руководит. Исполнителем может быть сотрудник этого отдела или его руководитель. У обычного сотрудника кнопки «Новая задача» нет. Поэтому сначала создайте отдел, добавьте в него людей и назначьте руководителя.

Пока не сделано: настройка статусов из интерфейса, комментарии и файлы, фильтры и поиск, обновление доски в реальном времени.

## Уведомления в Telegram

Бот пишет сотруднику в личный чат:

- исполнителю — когда ему назначили задачу или заявку (новую, переданную от другого сотрудника или перешедшую при отключении коллеги);
- руководителям отдела — когда исполнитель изменил срок; исполнителю — когда срок изменил руководитель;
- исполнителю и руководителям отдела — о новом комментарии. Текст комментария в Telegram не отправляется, только сообщение, что он есть.

О собственных действиях человек уведомлений не получает. В сообщении есть кнопка «Открыть в CRM».

Перед отправкой CRM ещё раз проверяет, что получатель по-прежнему видит задачу: если он за это время перестал быть исполнителем или руководителем отдела, сообщение не уходит. Если Telegram недоступен, действие в CRM всё равно выполняется, а отправка повторяется несколько раз.

Даты в сообщениях показываются в часовом поясе из настройки `NOTIFICATION_TIME_ZONE` (по умолчанию `Europe/Moscow`).

Пока не сделано: уведомления о смене статуса, чек-пойнтах и приглашениях в проекты, упоминания, напоминания о сроке, сводки по расписанию, личные настройки уведомлений, уведомления внутри CRM.

## Шаблоны заявок

Экран «Шаблоны заявок» есть только у администратора. Шаблон — это форма заявки.

- В редакторе задаются поля восьми типов (текст, число или сумма с валютой, дата, список, сотрудник, файл, «да / нет», ссылка на запись), их порядок и обязательность, а также чек-пойнты, с которыми будет создаваться заявка.
- Вы редактируете черновик. Сотрудники увидят изменения только после кнопки «Опубликовать»: она создаёт новую версию. Опубликованную версию изменить нельзя, поэтому уже поданные заявки остаются с той формой, с которой были созданы.
- У шаблона есть список отделов. Заявку по шаблону подаёт руководитель отмеченного отдела; если не отмечен ни один отдел, шаблон недоступен никому.
- Шаблон можно снять с использования и вернуть.

### Подача заявки по шаблону

Заявки по шаблонам подают руководители отделов. На доске у руководителя есть кнопка «Заявка по шаблону».

- В окне выбирается шаблон, отдел (из тех, которым шаблон доступен и которыми вы руководите), исполнитель, приоритет и срок, затем заполняется форма.
- Все значения проверяет сервер: обязательность, числа и их границы, даты, варианты списка, файл. В поле «сотрудник» можно указать только сотрудника или руководителя выбранного отдела. Если что-то не так, окно называет поле и причину.
- Заявка создаётся как задача с типом «Заявка», сразу назначается исполнителю и получает чек-пойнты шаблона. Файлы формы попадают в файлы задачи.
- В окне заявки есть блок «Форма» с ответами. Его видят те же, кто видит задачу: исполнитель, руководитель отдела, суперпользователь.
- Заявка навсегда остаётся с той версией формы, с которой подана. Если администратор опубликовал новую версию, пока вы заполняли форму, окно попросит открыть её заново.

### Задача сотруднику через Telegram

Руководитель может поставить обычную задачу конкретному сотруднику прямо в личном чате с ботом: команда `/task`.

- Бот спрашивает отдел (если их несколько), исполнителя, название, описание, срок и приоритет. Описание и срок можно пропустить.
- Срок вводится как `15.12.2026 14:30`; если указать только дату, срок будет до конца этого дня.
- Перед созданием бот показывает задачу целиком и создаёт её только после кнопки «Поставить задачу». `/cancel` отменяет.
- Права те же, что на сайте: задачи ставит руководитель и только для своих отделов. Исполнитель получает уведомление.

### Заявка через Telegram

Руководитель может подать заявку прямо в личном чате с ботом: команда `/request`.

- Бот по шагам спрашивает шаблон, отдел, исполнителя, название и каждое поле формы. Варианты выбираются кнопками, необязательные вопросы можно пропустить.
- Даты вводятся как `15.12.2026` или `15.12.2026 14:30`. Файл отправляется документом или фото, до 20 МБ (ограничение Telegram для ботов).
- В конце бот показывает всю заявку и создаёт её только после кнопки «Подать заявку». Команда `/cancel` отменяет заполнение.
- Правила те же, что на сайте: те же шаблоны, те же проверки значений, тот же результат. Приоритет ставится обычный, срок не задаётся — их можно поменять в CRM.
- В группах команда не работает. Незаконченное заполнение забывается через 30 минут.

Пока не сделано: значения по умолчанию, мини-приложение Telegram, запуск заявки из группы.

## Проекты

Экран «Проекты» виден всем: сотрудник видит проекты, в которых участвует, руководитель — ещё и проекты своего отдела.

- Проект создаёт руководитель для своего отдела.
- Сотрудника своего отдела руководитель добавляет сразу.
- Сотрудника другого отдела можно только пригласить: приглашение приходит руководителю его отдела в блок «Приглашения вашим сотрудникам». Пока оно не согласовано, сотрудник в проекте не участвует и проект не видит.
- Участие в проекте показывает проект и список участников, но **не открывает задачи** других людей.

Задачу можно отнести к проекту: руководитель выбирает проект при создании задачи или при редактировании. На карточке проект показан перед отделом. Это только метка для группировки — участники проекта не получают доступа к задаче.

## Файлы

В окне задачи есть блок «Файлы». Прикреплять могут исполнитель и руководитель отдела, скачивать — все, кто видит задачу. Убрать файл может руководитель.

- Принимаются PDF, Word, Excel, изображения (PNG, JPEG, GIF, WebP) и ZIP-архивы до 100 МБ. Тип определяется по содержимому, а не по названию. Документы с макросами не принимаются. Антивирусной проверки нет.
- Файл всегда скачивается, а не открывается внутри CRM.
- Где хранятся файлы, задаёт `FILE_STORAGE` в `.env`: `local` — том Docker `crm-files` (для пробного запуска), `s3` — объектное хранилище (для рабочей версии; нужны адрес, бакет и ключи, см. `.env.example`). Бакет должен быть закрытым.

## Комментарии

В окне задачи есть блок «Комментарии». Писать могут исполнитель и руководитель ответственного отдела, читать — все, кто видит задачу. Изменить можно только свой комментарий, срок правки не ограничен; прежний текст сохраняется в базе, а рядом появляется отметка «изменён». Удалить комментарий может только руководитель отдела: комментарий скрывается у всех. В архивной задаче комментарии только читаются.

## Статусы задач

Экран «Статусы» (только администратор) настраивает колонки доски: добавить статус, переименовать, поменять порядок, отметить, из какого статуса в какой можно переводить задачу. Тип статуса (новая, в работе, завершена, отменена) выбирается при создании и потом не меняется. Содержимое задач на этом экране не показывается — только их количество.

Статус не удаляется, а убирается с доски. Если в нём есть задачи, администратор сам выбирает, на какой статус того же типа их перенести: автоматически замена не подбирается. Перенос записывается в историю каждой задачи. Убранный статус можно вернуть на доску; перенесённые задачи при этом обратно не возвращаются.

## Отделы

Экран «Отделы» (администратор): создание отделов, состав, руководители. У сотрудника может быть несколько отделов, один из них основной — первым становится тот, куда его добавили первым, сменить может только администратор. У отдела может быть несколько руководителей, один из них ответственный: ему перейдут открытые задачи сотрудника при отключении учётной записи. Руководитель видит свои отделы и их сотрудников и может создавать сотрудников в своём отделе; менять состав отделов и отключать учётные записи может только администратор.

## Новый сотрудник

1. Администратор открывает «Сотрудники», вводит имя и логин и нажимает «Создать». CRM один раз показывает команду вида `/start КОД` (код действует 30 минут; пока Telegram не привязан, можно выдать новый).
2. Администратор передаёт команду сотруднику лично. Сотрудник отправляет её боту CRM в личном чате.
3. Бот отвечает, что Telegram привязан, и присылает сообщение с кнопкой «Задать пароль». По ней сотрудник сам задаёт пароль (не короче 12 символов). Администратор пароль не знает. Ссылка действует 30 минут; новую присылает команда `/password`.
4. Сотрудник входит: логин, пароль, подтверждение в Telegram.

Отключение учётной записи действует сразу: открытые сессии, ожидающие входы, коды и ссылки перестают работать. Забытый пароль этой ссылкой не меняется — восстановление доступа выполняет администратор (пока не реализовано).

Адрес, который бот подставляет в ссылку, задаётся в `WEB_PUBLIC_URL`. Если сервер не может обращаться к Telegram напрямую, адрес Bot API меняется в `TELEGRAM_API_BASE_URL` (свой сервер Bot API или ретранслятор под вашим контролем).

Пока не сделано: изменение данных сотрудника и назначение ролей из интерфейса, восстановление доступа, режим webhook. Подробности — в `docs/SECURITY.md` и `docs/TELEGRAM.md`.

## Изменение API и схемы данных

- После изменения эндпоинтов: `pnpm contracts:export`, затем `pnpm contracts:generate`, и закоммитьте `packages/contracts`.
- После изменения моделей: `uv run python manage.py makemigrations` в `apps/api`, закоммитьте миграцию. Применённые миграции не редактируются. Правила — в `docs/DATABASE.md`.

## Зависимости

- Версии закреплены точно; lockfile'ы — `pnpm-lock.yaml` и `uv.lock`.
- Новый релиз можно установить только через 7 дней после публикации (настроено в `pnpm-workspace.yaml` и `pyproject.toml`). Исключение для срочного исправления безопасности оформляется там же с комментарием — порядок в `docs/ARCHITECTURE.md`.

## Секреты

- `.env` и любые реальные учётные данные в репозиторий не попадают; в `.env.example` только заглушки.
- CI использует собственные тестовые значения, не имеющие силы за пределами прогона.

## Сброс и откат

- Сброс локальных данных: `docker compose down --volumes`, затем `docker compose up --build --wait`.
- Откат изменения: `git revert <коммит>`; каждая задача S0 оформлена отдельным коммитом.

## Приоритет источников

1. Явно согласованные продуктовые решения в `docs/PRD.md` и `docs/DECISIONS.md`.
2. Подробные политики в `docs/PERMISSIONS.md`, `docs/SECURITY.md`, `docs/TELEGRAM.md`.
3. Архитектурные предложения в остальных документах, пока они не конфликтуют с требованиями.
4. При противоречии или пробеле бизнес-политика не придумывается: вопрос регистрируется в `docs/OPEN_QUESTIONS.md` и ждёт решения.

Открытые вопросы не считаются утверждёнными: объём файлов, RPO/RTO, авторизация при потере Telegram, часть политик удаления и архивирования и другие.
